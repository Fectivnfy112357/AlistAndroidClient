# UI 性能系统优化设计

**日期：** 2026-07-15
**状态：** 待用户复核

## 1. 背景与目标

当前首页、音乐库、设置页在连续滚动后出现明显不跟手；底部主 Tab 切换不流畅；音乐任意子页进入播放页会掉帧；播放页加载态和播放过程也存在卡顿。

验收设备为通过 Wi-Fi ADB 连接的 `25102RK69C`（Android 16，1200×2608，最高 120Hz）。现有累计 `gfxinfo` 显示 UI 线程帧时间 P50 约 8ms、P90 约 14ms、P95 约 18ms，而 GPU P95 约 6ms。120Hz 的单帧预算约为 8.3ms，因此主要方向是降低主线程组合、测量、布局与状态分发开销，而非牺牲整体视觉风格来规避 GPU 压力。

本次目标：

- 首页、音乐库、设置页连续滚动时保持稳定响应，不因多次往返滚动逐步恶化。
- 五个主 Tab 切换不产生可感知停顿。
- 音乐库各子页进入播放页时避免主线程长帧。
- 播放页加载、进度更新、歌词滚动互不放大重组范围。
- 建立可重复的真机性能采样场景，使优化前后可比较并能发现回退。

不在本次范围：重新设计页面视觉、替换播放内核、修改服务器接口、实现完整 Macrobenchmark 独立模块。

## 2. 优化原则

1. **先测量后修改。** 每个目标场景先清零 `gfxinfo`，执行固定操作序列并保存帧统计；必要时采集 Perfetto/系统跟踪定位长帧。
2. **按状态所有权隔离更新。** 高频播放进度、歌词行号、滚动位置只在最小消费子树读取，不能触发整页或 Lazy 容器重组。
3. **Lazy 内容可复用。** 所有动态条目提供稳定 `key` 和准确 `contentType`；排序、映射、分组和格式化不在 item 热路径重复执行。
4. **主线程不做阻塞工作。** 图片解码、数据库聚合、歌词解析、缓存统计和网络读取在注入的后台 dispatcher 执行；UI 仅接收准备好的不可变结果。
5. **导航避免双重高成本绘制。** 主 Tab 切换保持无页面级动画；进入播放页仅保留轻量位移动画，避免源页和目标页同时透明混合或重复背景绘制。
6. **保留视觉意图。** 保留现有配色、层级和主要过渡，只替换透明叠层、重复背景、无边界动画等高成本实现。

## 3. 测量方案

### 3.1 固定场景

每个场景在相同 Debug/性能构建、相同设备刷新率设置和相同数据集下至少执行三轮：

- 首页：进入后上下快速滚动各 5 次。
- 音乐库：歌曲、专辑、艺术家子页分别滚动，子页间往返切换。
- 设置页：上下快速滚动各 5 次。
- 主 Tab：按“首页 → 文件 → 音乐 → 传输 → 设置 → 首页”循环 3 次。
- 播放页：分别从歌曲、专辑、艺术家入口进入播放页并返回。
- 播放态：观察 loading、封面出现、进度推进和歌词自动定位全过程。

### 3.2 指标

- `dumpsys gfxinfo`：总帧数、janky frames、frame deadline missed、slow UI thread、P50/P90/P95/P99。
- 屏幕模式：操作期间实际 render refresh rate，确认采样窗口处于 120Hz。
- Perfetto（仅热点场景）：主线程长任务、Compose composition/layout/draw、图片解码、Binder/数据库调用。
- 功能回归：页面内容、滚动位置恢复、播放控制、歌词同步、返回栈行为。

主要通过标准：在目标真机 120Hz 场景中，优化后的 P50 明显低于 8.3ms，P90/P95 和 deadline missed 相比基线显著下降；三轮结果不得出现连续操作后逐轮恶化。若设备调度或 Debug 开销导致绝对阈值不稳定，以同构建配置下的前后对照和 Perfetto 长帧消除为最终依据。

## 4. 分层设计

### 4.1 根布局与导航

- 审查 `AppNavHost`、`AppBottomNavBar`、`AppScaffold`、全局背景和导航 transition。
- 保证全局渐变与装饰只绘制一次，子页面不重复铺设等价背景。
- 主 Tab 使用保存/恢复状态的单顶导航，并验证不会创建重复目的地或重复 ViewModel 工作。
- 底栏只订阅当前目的地所需的最小状态；稳定导航回调和条目模型。
- 播放页 transition 不进行全屏 alpha 混合；目标页在首帧即可绘制轻量占位。

### 4.2 首页与设置页

- 将列表条目拆成可跳过的稳定组合边界，补全 `key`/`contentType`。
- 避免在组合及 Lazy item 中重复进行集合查找、字符串拼接和派生模型构造。
- ViewModel 输出 UI 所需的不可变、已派生数据；独立 Flow 不在屏幕根部无差别合并高频更新。
- 设置页的缓存统计、管理数据加载和文本输入状态避免在每次进入或重组时重复触发昂贵工作。

### 4.3 音乐库

- 检查歌曲、专辑、艺术家列表/网格的稳定键、内容类型、分页可见数量和图片模型身份。
- 把领域模型到 UI 模型的全量映射、专辑封面关联等计算移出高频组合路径，并避免数据库任一表变化导致所有集合重建。
- Mini Player 仅订阅当前歌曲、播放状态等实际展示字段，不接收播放位置 tick。
- 图片请求采用固定目标尺寸和稳定缓存键，避免滚动时解码过大图片或重复创建请求。

### 4.4 播放页

- 播放页面拆为静态元信息、封面、控制区、进度区、歌词区五个独立重组边界。
- 进度 Flow 只驱动 Slider 与时间文本；拖动状态不提升到整页。
- 当前歌词索引使用去重后的派生 Flow；自动滚动只在索引真正变化时执行，并避免每次 tick 启动重复动画。
- 封面解码在后台完成，限制解码尺寸，并缓存同一歌曲结果；加载占位不触发布局尺寸变化。
- loading 指示器限定尺寸和绘制范围；播放准备状态不应让整页结构在 loading/content 之间反复替换。

### 4.5 稳定性与 Compose 编译器信息

- 对真正不可变的 UI 模型使用正确的稳定性表达；不对内部可变集合错误标注 `@Immutable`。
- 必要时启用 Compose compiler stability/recomposition 报告用于诊断，不把报告配置带入日常 Release 构建流程。
- 不为性能目的盲目 `remember` 普通常量；只缓存可测量的对象分配或昂贵派生结果。

## 5. 测试策略

- 先为可抽取的派生逻辑、去重逻辑、可见条目计算和导航策略补失败测试，再修改生产代码。
- Compose 测试验证列表稳定身份、页面状态分支和播放进度更新不会改变无关 UI 行为。
- 现有单元测试、Compose/Robolectric 测试、Lint 与 Debug 构建必须通过。
- 真机安装后重复第 3 节全部场景，保存优化前后数据与结论到实施报告。

性能测试不能只依赖 Debug 首次运行；正式对比前先预热应用和关键页面，并确保两组数据使用相同构建类型、设备温度与刷新率条件。

## 6. 风险与回退

- 状态拆分可能造成 UI 更新遗漏：通过 UDF 测试和播放状态回归覆盖。
- Lazy key 选择不正确可能冲突：只使用路径、实体 ID 等稳定唯一值，不使用索引。
- 导航状态恢复调整可能改变返回栈：覆盖主 Tab 往返、子页返回和播放页返回场景。
- 图片降采样可能影响清晰度：按实际显示尺寸和设备密度请求，不使用任意低分辨率常量。
- 120Hz 指标受系统动态刷新率和温控影响：记录实际刷新率，多轮采样，并保留 60Hz 对照。

## 7. 实施顺序

1. 建立真机基线和可复跑采样脚本。
2. 优化根布局、背景、底栏和导航切换。
3. 优化首页与设置页滚动。
4. 优化音乐库列表、图片与状态模型。
5. 优化播放页进入、loading、进度和歌词。
6. 完整构建、测试、GitNexus 变更检测与真机前后对比。
